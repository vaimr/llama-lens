## 1. Общая архитектура

### 1.1 Диаграмма архитектуры

```
                     config/hosts.yaml (N хостов, gitignore)
                               │
┌─────────────────────────────▼──────────────────────────────┐
│  FastAPI однопроцессный :8000 (локальная установка)         │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ MonitorRegistry                                       │  │
│  │  ├─ HostMonitor[ai]     ├─ HostMonitor[host2] ...    │  │
│  │  │   ├─ LlamaPoller 1s  │   (каждый хост независимо: │  │
│  │  │   ├─ SshPoller   2s  │    сбор + буфер + события) │  │
│  │  │   ├─ LogPoller (journal поток)                   │  │
│  │  │   ├─ RingBuffer (3600@1s + 1800@2s)               │  │
│  │  │   └─ EventDetector (старт/окончание задачи, out/in)│  │
│  └──────────────────────────────────────────────────────┘  │
│  REST: /api/hosts · /api/hosts/{id}/overview|history|events │
│  WS:   /ws/hosts/{id} (push с тиком 1с, настраиваемо)       │
│  Статика: frontend/dist (результат сборки Vue3)             │
└─────────────────────────────▲──────────────────────────────┘
                               │ WS 1с / HTTP фоллбек
               ┌───────────────┴───────────────┐
               │  Браузер (Vue3 + ECharts)      │
               │  /            Портал хостов    │
               │  /host/:id  Детали одного хоста│
               └───────────────────────────────┘

Источники данных (каждый хост): llama HTTP API (8080) + SSH только-чтение пакетные команды (22)
```

## 3. Многохостовый дизайн

### 3.1 Основная абстракция

```python
class HostMonitor:
    """Одна единица мониторинга на каждый хост"""
    def __init__(self, cfg: HostConfig): ...
    def start(self): ...      # Запуск LlamaPoller + SshPoller + push-задачи
    def stop(self): ...
    def snapshot(self) -> dict: ...   # Текущий снимок (вкл. alerts)
    def history(self, window_s: int) -> dict: ...
    def events(self, limit: int) -> list: ...

class MonitorRegistry:
    """Управление всеми HostMonitor"""
    def load(self, path: str): ...    # Разбор hosts.yaml
    def get(self, host_id: str) -> HostMonitor: ...
    def list(self) -> list: ...       # Данные портала (сводка по каждому хосту)
```

- Каждый HostMonitor запускает 3 независимых async-задачи: LlamaPoller, SshPoller, WsPusher
- Исключения в любой задаче перехватываются и логируются, не влияя на другие задачи и другие хосты
- При запуске Registry загружает все хосты; изменения конфига требуют перезапуска (горячая загрузка не реализована)

### 3.2 Конфигурация hosts.yaml (полный пример)

```yaml
# config/hosts.yaml (gitignore; шаблон см. hosts.example.yaml)
global:
  push_interval: 1.0        # Интервал push WS (секунды)
  history:
    llama_points: 3600      # Точки кольцевого буфера метрик llama @1с (1ч)
    host_points: 1800       # Точки кольцевого буфера метрик host @2с (1ч)
  thresholds:               # Пороги по умолчанию для всех хостов
    gpu_util:   { warn: 80, danger: 90 }
    gpu_mem:    { warn: 85, danger: 95 }
    gpu_temp:   { warn: 75, danger: 85 }
    gpu_power:  { warn: 85, danger: 95 }   # Процент от лимита мощности
    cpu:        { warn: 80, danger: 90 }
    mem:        { warn: 85, danger: 95 }
    disk:       { warn: 80, danger: 90 }

hosts:
  - id: ai
    name: "AI-хост (ai.lan)"
    llama:
      host: ai.lan
      port: 8080
      interval: 1.0         # Интервал опроса /health + /slots (секунды)
      slow_interval: 30.0   # Интервал опроса /props + /v1/models (секунды)
    ssh:
      host: ai.lan
      port: 22
      user: root
      password: ${AI_SSH_PASS}   # Чтение из переменной среды .env, не хранить явно
      interval: 2.0         # Интервал пакетного сбора (секунды)
      keepalive: 15         # SSH keepalive (секунды)
    process:
      name: llama-server    # Имя целевого процесса для мониторинга
    log:
      unit: llama-server    # Имя systemd unit (journalctl -u)
      follow: true          # Поточное следование (false = периодический --since pull)
      catchup_sec: 30       # Секунды для догрузки после переподключения
    systemd_unit: llama-server.service
    thresholds: {}          # Переопределение на каждый хост (опционально, структура как global)
```

### 3.3 Процесс добавления нового хоста

1. Добавить запись в hosts.yaml (id должен быть уникальным)
2. Добавить соответствующий SSH-пароль в .env (если используется ссылка на переменную среды)
3. Перезапустить панель → на портале автоматически появится новая карточка

Без изменения кода.

## 4. Дизайн слоя сбора

### 4.1 LlamaPoller (1с)

Эндпоинты и частота:

| Эндпоинт | Частота | Назначение |
|---|---|---|
| GET /health | 1с | Проверка доступности |
| GET /slots | 1с | Состояние слотов + вход для дифференциала скорости |
| GET /props | 30с | Информация о модели, параметры по умолчанию, модальности |
| GET /v1/models | 30с | Количество параметров / размер эмбеддинга / словарь / размер файла |

Алгоритм дифференциала скорости (для каждого слота):

```
state: prev_task_id, prev_decoded, prev_prompt_processed, prev_ts, task_start_ts

on_poll(slot):
  now = time(); dt = now - prev_ts
  if slot.is_processing:
    if prev_task_id is None:
        task_start_ts = now                      # Событие старта задачи
    if slot.id_task != prev_task_id or slot.n_decoded < prev_decoded:
        # Новая задача (или граница задачи): сброс базовой линии, скорость за этот тик = 0
        prev_task_id = slot.id_task
        prev_decoded = slot.n_decoded
        prev_prompt_processed = slot.n_prompt_tokens_processed
        gen_speed = 0; prompt_speed = 0
    else:
        gen_speed    = (slot.n_decoded - prev_decoded) / dt
        prompt_speed = (slot.n_prompt_tokens_processed - prev_prompt_processed) / dt
        prev_decoded = slot.n_decoded
        prev_prompt_processed = slot.n_prompt_tokens_processed
  else:
    if prev_task_id is not None:
        # Событие окончания задачи: total tokens = последний n_decoded, длительность = now - task_start_ts
        emit(task_end, total_tokens, duration, avg_tps)
        prev_task_id = None
    gen_speed = 0; prompt_speed = 0
  prev_ts = now
```

- Событие старта задачи: is_processing false→true → записать task_start (ID задачи, кол-во prompt-токенов)
- Изменение модели: изменение /props.model_path → событие model_change
- Обработка сбоев: таймаут запроса 3с; 3 неудачи подряд → online=false + событие llama_down; восстановление → событие llama_up; в период оффлайна сохраняется последние данные

### 4.2 SshPoller (2с)

Управление соединением:
- paramiko SSHClient, AutoAddPolicy (при первом соединении автоматически доверяет отпечатку и логирует)
- transport.set_keepalive(15)
- Разрыв: экспоненциальная задержка переподключения 1с→2с→4с→...→30с максимум; при разрыве событие ssh_down, при успешном переподключении — ssh_up
- Статическая информация (собирается при первом соединении один раз): hostname, ядро, версия ОС (/etc/os-release), модель CPU, количество ядер

Пакетные команды за цикл (1 exec, один сетевой переход, всё только-чтение):

```bash
echo ==GPU==
nvidia-smi --query-gpu=index,name,driver_version,memory.total,memory.used,memory.free,utilization.gpu,utilization.memory,temperature.gpu,power.draw,power.limit,fan.speed,clocks.current.graphics,clocks.current.memory,pcie.link.gen.current,pcie.link.width.current,pstate,temperature.memory,ecc.errors.corrected.volatile.total,ecc.errors.uncorrected.volatile.total,clocks_throttle_reasons.active,cuda_version --format=csv,noheader,nounits
echo ==APPS==
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv,noheader,nounits
echo ==STAT==
cat /proc/stat
echo ==MEM==
grep -E '^(MemTotal|MemFree|MemAvailable|Buffers|^Cached|SwapTotal|SwapFree)' /proc/meminfo
echo ==LOAD==
cat /proc/loadavg
echo ==UPTIME==
cat /proc/uptime
echo ==NET==
cat /proc/net/dev
echo ==DISKIO==
grep -E '^(sd|nvme|vd|dm)' /proc/diskstats
echo ==DF==
df -B1 --output=target,size,used,avail,pcent / /share 2>/dev/null
echo ==PROC==
PID=$(pgrep -x llama-server | head -1)
if [ -n "$PID" ]; then
  echo P:$PID
  awk '{print $14, $15, $23}' /proc/$PID/stat    # utime stime vsize
  grep -E '^(VmRSS|VmSize|Threads)' /proc/$PID/status
  ps -o pcpu=,pmem=,etime= -p $PID
  tr '\0' ' ' < /proc/$PID/cmdline; echo
fi
echo ==PS==
ps -eo pid,comm,pcpu,pmem,rss --no-headers 2>/dev/null
echo ==PSTICKS==
awk 'FNR==1 { n=split(FILENAME, p, "/"); pid=p[n-1]; i=index($0, ") "); if (i > 0) { s=substr($0, i+2); m=split(s, a, " "); if (m >= 13) print pid, a[12], a[13] } }' /proc/[0-9]*/stat 2>/dev/null
echo ==PROCS==
ls /proc | grep -c '^[0-9]'
```

Расчёт дифференциалов (бэкенд DiffEngine, на основе двух последовательных сэмплов):
- Общий CPU% хоста = 1 - Δidle/Δtotal (строка суммарного cpu)
- CPU% каждого ядра = 1 - Δidle_i/Δtotal_i (строки cpu0..cpu5)
- Реалтайм CPU% процесса = Δ(utime+stime)/Δt/CLK_TCK (относительно одного ядра)
  - Зависший процесс: поле 14/15 в /proc/<pid>/stat (тикерные тики, точность 10мс)
  - Топ-лист: секция ==PSTICKS== (одиночная awk читает utime/stime для всех /proc/<pid>/stat, точность 10мс, связывается по PID с секцией ==PS==)
  - Примечание: stime в procps — это время запуска (start time), а не системное CPU-время; столбец utime недоступен (вывод -); столбец time имеет точность только 1с, при окне сэмплов 2с CPU% квантуется в ступенчатые значения 0/50/100/150 (в простое все 0, выглядит как «поддельные данные»), поэтому необходимо читать напрямую из /proc
- Сортировка по CPU: реалтайм CPU% → накопленное CPU-время → RSS; по MEM: RSS → реалтайм CPU% (каждый по топ-8, сортировка на бэкенде)
- Скорость диска = Δsectors×512/Δt
- Скорость сети rx/tx = Δbytes/Δt
- Первый сэмпл без базовой линии → дифференциальные метрики за этот тик = null

### 4.3 EventDetector

Машина состояний (на каждый хост):

```
llama: online ⇄ offline   (3 неудачи подряд /health → offline)
ssh:   connected ⇄ disconnected
task:  idle → running (task_start) → idle (task_end, со статистикой)
model: изменение props.model_path → model_change
prefill: первая строка prompt в задаче → prefill_start (с общим кол-вом prompt-токенов)
alert:   check_alerts(alerts) отслеживает изменения уровня по метрикам (normal/warn/danger), событие при изменении (минимальный интервал между событиями 30с, первое наблюдение только записывает базовую линию)
```

Кольцевой буфер событий: 200 записей, поля {ts, level, type, msg}
- task_start/task_end приоритетно берут строки логов (launch_slot_ / release) как источник, со всей статистикой (скорость принятия MTP, использование контекста, длительность)
- Событие boot: строка лога «model loaded» → llama_boot (с информацией о загрузке)
- prefill_start: LogPoller выдаёт на первой строке prompt каждой задачи (дедупликация по ID задачи, сброс при окончании/перезапуске задачи)
- alert: HostMonitor вызывает check_alerts после каждого evaluate_alerts снимка; llama/ssh не дублируются (уже есть отдельные события up/down)

### 4.4 LogPoller (поток логов)

Источник данных: `journalctl -u {log.unit}` (systemd journal, только-чтение)

Метод сбора:
- Выделенный SSH channel (тот же transport, что и SshPoller, отдельный channel) запускает `journalctl -u llama-server -f -o short-iso --no-pager -n 0` для поточного следования
- Разрыв channel: переподключение + сначала `--since "N seconds ago"` (catchup_sec, по умолчанию 30с) для догрузки, предотвращение потери строк
- follow=false (режим fallback): периодический (2с) pull `--since "@<last_ts>"` новых строк
- Первое подключение: загрузка последнего блока запуска (200 строк до «listening»), разбор boot-информации

Формат строки лога (short-iso):

```
2026-08-28T18:11:25+08:00 ai llama-server[55646]: 50.44.267.087 I slot      release: id  0 | task 14847 | stop processing: n_tokens = 201047, truncated = 0
└─ syslog время ──────────┘ └host┘ └unit[pid]┘  └─ внутреннее время llama.cpp ──┘ └L┘ └subsys┘ └function┘ └─ сообщение ─┘
```

Правила парсинга (regex, последовательное совпадение):

| # | Шаблон (упрощённый) | Событие | Извлекаемые поля |
|---|---|---|---|
| 1 | `slot print_timing: id (\d+) \| task (\d+) \| n_decoded = (\d+), tg = ([\d.]+) t/s, tg_3s = ([\d.]+) t/s` | decode_tick | task_id, n_decoded, tg, tg_3s |
| 2 | `slot print_timing: id (\d+) \| task (\d+) \| prompt processing, n_tokens = (\d+), progress = ([\d.]+), t = ([\d.]+) s / ([\d.]+) tokens per second` | prompt_tick | task_id, n_tokens, progress, elapsed_s, speed_tps |
| 3 | `slot print_timing: ... prompt eval time = ([\d.]+) ms / (\d+) tokens \(([\d.]+) ms per token, ([\d.]+) tokens per second\)` | task_summary.prompt | prompt_ms, prompt_tokens, prompt_speed_tps |
| 4 | `slot print_timing: ... eval time = ([\d.]+) ms / (\d+) tokens \(([\d.]+) ms per token, ([\d.]+) tokens per second\)` | task_summary.eval | eval_ms, decoded_tokens, gen_speed_tps |
| 5 | `slot print_timing: ... total time = ([\d.]+) ms / (\d+) tokens` | task_summary.total | total_ms, total_tokens |
| 6 | `slot print_timing: ... graphs reused = (\d+)` | task_summary.graphs | graphs_reused |
| 7 | `slot print_timing: ... draft acceptance = ([\d.]+) \((\d+) accepted / (\d+) generated\), mean len = ([\d.]+)` | task_summary.mtp | acceptance, accepted, generated, mean_len |
| 8 | `slot release: id (\d+) \| task (\d+) \| stop processing: n_tokens = (\d+), truncated = (\d+)` | task_end | ctx_used, truncated |
| 9 | `slot get_availabl: id (\d+) \| task -1 \| selected slot by (LRU\|LCP similarity)(?:, f_sim_best = ([\d.]+).*)?(?:, f_keep = ([\d.]+))?` | slot_select | method, f_sim_best, f_keep |
| 10 | `slot launch_slot_: id (\d+) \| task (\d+) \| processing task, is_child = (\d+)` | task_start | task_id, is_child |
| 11 | Стартовые строки: `loading model '(.+)'` / `n_slots = (\d+), n_ctx_slot = (\d+), kv_unified = '(\w+)'` / `creating MTP draft context` / `upgrading K from (\S+) to (\S+)` / `verbosity = (\d+)` / `listening on (\S+)` / строки уровня `W` | boot_info | model, n_slots, n_ctx_slot, kv_unified, mtp_draft, kv_upgrade, verbosity, listening, warnings[] |

Машина состояний (текущее состояние, обновляется по строке):

```
phase: idle → prompt_processing (prompt_tick) → decoding (decode_tick) → idle (task_end)
current: {phase, task_id, n_decoded, tg, tg_3s, prompt_progress, prompt_speed, prompt_total_tokens, prompt_elapsed_s, is_child, started_at}
started_at: временная метка начала задачи (записывается при launch, очищается при task_end; фронтенд вычисляет «время работы»)
last_prefill: {speed, ts, progress, n_tokens}   # Обновляется каждой строкой prompt, очищается при перезапуске llama
context: {used (n_tokens последнего task_end), total (boot n_ctx_slot), pct, remaining, truncated}
mtp:     {acceptance, accepted, generated, mean_len}   # Обновляется при task_end
kv:      {f_keep, f_sim_best, selection}               # Обновляется при slot_select
boot:    {...}                                          # Обновляется при boot_info
```

Приоритет источника скорости:
1. tg_3s из логов (3-секундное окно, расчёт на сервере) — основной
2. Дифференциал /slots n_decoded (1с) — фоллбек при недоступности логов
- Фронтенд помечает источник данных (log / API)

Обработка сбоев:
- Разрыв channel → переподключение + догрузка; в период log_available=false, скорость фоллбэк на дифференциал /slots
- Ошибка парсинга строки → пропуск и подсчёт (счётчик parse_error), не влияет на другие строки
- Перезапуск llama-server (изменение PID) → сброс машины состояний, повторный разбор boot-информации

## 13. Локальный CLI (llamalens)

Полноэкранный TUI в стиле htop, **работающий локально на каждом отслеживаемом хосте**, с тем же источником данных, что и страница деталей одного хоста веб-панели (те же поля сбора, пороги, события, правила парсинга логов). Нулевые зависимости во время выполнения: один статический бинарный файл (`CGO_ENABLED=0`), на целевом хосте не нужны Go / Python / pip.

### 13.1 Выбор технологий

| Параметр | Выбор | Обоснование |
|---|---|---|
| Язык | Go 1.24 | Один статический бинарный файл, кроссплатформенность, удобная работа с `/proc` напрямую |
| TUI-фреймворк | bubbletea + lipgloss (charm) | Управляет жизненным циклом терминала (raw-режим / альтернативный буфер / курсор / resize / восстановление при выходе), **никаких ручных ANSI-последовательностей** — устраняет полноэкранное искажение, вызванное ручным кодированием в ранних версиях |
| Рендеринг | lipgloss стили + самописные sparkline/бары | Те же цвета, что и тема Terminal фронтенда (cyan/green/amber/red) |

### 13.2 Архитектура (однопроцессный, без сетевых зависимостей)

```
llamalens (однопроцессный)
├── collect.LlamaCollector   Локальный HTTP: /slots@1с, /props+/v1/models@30с
├── collect.HostCollector    Прямое чтение /proc@2с (stat/meminfo/loadavg/net/dev/diskstats/[pid]/stat) + nvidia-smi@2с + systemctl show
├── logparse.Poller          11 типов regex логов + машина состояний (тот же источник, что backend/pollers/log_poller.py)
├── collect.JournalCollector journalctl -u <unit> -f поток (разрыв — --since догрузка; изменение PID — повторная загрузка блока boot)
├── model.World              Агрегация: дифференциальный движок + кольцевой буфер (llama@1с/3600, host@2с/1800) + обнаружение событий + оценка алертов
└── ui.App (bubbletea)       4fps рендеринг; клавиши q/p/t/g; WindowSizeMsg адаптация
```

Поток данных идентичен веб-версии: сборщики → World.Tick (1с: приоритет скорости log tg_3s > дифференциал /slots, запись в кольцо, построение снимка, оценка алертов) → снимок → рендеринг.

Состояние «задача в процессе» определяется по **API /slots** (любой slot `is_processing` = в процессе): журнал имеет задержку/потерю строк, фаза лога отстает от API при старте задачи; если ориентироваться на фазу лога, получится «скорость токенов есть, а статус idle». Фаза лога используется только для уточнения метки (decoding/prefill); при генерации и отставании лога отображается «Generating». ID задачи тоже: в процессе берётся `slot.id_task` (task_id из лога может быть остатком предыдущей задачи).

Детали сбора nvidia-smi: `--query-gpu` содержит `uuid`, `--query-compute-apps` содержит `gpu_uuid`, процесс **привязан к карте** (на каждой карте строка «использование» показывает VRAM этой карты; один PID появляется по строке на каждую использованную карту; при отсутствии `gpu_uuid` в старых драйверах фоллбэк — все на первую карту). Обратите внимание: CSV содержит пробелы после запятой (`" 17920"`), парсинг чисел обязан trim, иначе `ParseInt` всегда возвращает 0 (ранее вызывало «GPU usage 0MB»).

### 13.3 Ограничения корректности рендеринга (ключевые)

Ранние версии с ручными ANSI-последовательностями вызывали полноэкранное искажение (вид报文状). После переписывания введены три обязательных ограничения, проверенные на PTY:

1. **Не писать ANSI вручную**: жизненный цикл терминала полностью на bubbletea; стили только через lipgloss.
2. **ANSI-aware ширина/обрезка**: `displayWidth`/`trunc` пропускает байты ANSI-последовательностей (CSI-引导符 `[` и terminating byte различаются), CJK считается 2 колонки; никогда не обрезать посреди ANSI-последовательности (иначе утечка кодов цвета + выход за ширину строки).
3. **Ширина строки ≤ ширина терминала−1**: заполнение последнего столбца вызывает автоматический перенос терминала, сдвигая все последующие строки вниз, с перекрытием между кадрами. `Render()` в конце обрезает каждую строку `trunc(l, w-1)`; lipgloss `Width/Height` — внутренние размеры (без рамки), для внешних размеров панели нужно сначала вычесть 2.
4. **Приоритет обрезки TopBar**: левая секция — «Бренд · Хост · Модель  Статус онлайн», при нехватке места сначала обрезать имя модели, затем имя хоста, гарантируя, что статус онлайн всегда виден (полная левая обрезка сначала уберёт именно статус онлайн в конце).
5. **Цвет рамки ярче фронтенда**: рамка фронтенд-карточек `#242428` зависит от фона карточки; у TUI нет фона, поэтому на тёмном терминале почти невидима, поэтому рамка TUI использует `#55555e` (остальные цвета совпадают с темой Terminal фронтенда).
6. **Выравнивание правого края по строкам**: общая ширина каждой строки должна точно равняться доступной ширине (ширина терминала−2). `lipgloss.JoinHorizontal` не вставляет разделительные колонки (легко ошибочно принять за место — старый код резервировал (n−1) gap-колонки, которых фактически не было, из-за чего правые края строк были неровными). При разбивке на колонки последняя колонка берёт остаток: `cw=usable/n`, `cwLast=usable−cw×(n−1)`.

### 13.4 Конфигурация (флаги, значения по умолчанию совпадают с ai.lan)

`--llama-host 127.0.0.1 --llama-port 8080 --process llama-server --unit llama-server --log journal --mounts / --once --dump-frame <file> --no-color`. `--dump-frame` для отладки: исходные байты каждого кадра рендеринга (вкл. ANSI) записываются в файл (каждый раз перезаписывая), при воспроизведении проблем отображения остановите по `p` — кадр сохранится. `--no-color` для отладки: `lipgloss.SetColorProfile(termenv.Ascii)` рендеринг в чистом тексте (lipgloss читает глобальный profile при рендеринге, настройка до запуска действует глобально). Имя процесса / unit / порт должны совпадать с целевым хостом в `hosts.yaml` (см. README «Подготовка целевого хоста» — 4 условия). Имя процесса: сначала точное совпадение `/proc/<pid>/comm`, при неудаче фоллбэк на basename cmdline argv[0] (ядро обрезает comm до 15 символов, кастомная сборка может принимать полное имя напрямую, например `llama-cpp-turboquant`). Имя модели в TopBar совпадает с веб TopBar: alias — полное имя при полном пути, только имя файла при алиасе; карточка модели показывает полное имя + размер + mmproj (mmproj берётся из cmdline процесса `--mmproj`).

### 13.5 Отношения с веб-панелью

CLI — **только-чтение sidecar**: не проходит через бэкенд, не записывает файлы, не меняет состояние llama-server. Поля сбора, пороги, типы событий, regex парсинга логов — тот же источник, что и бэкенд (бэкенд на Python, CLI на Go, правила поддерживаются отдельно, но семантика согласована). При обновлении полей сбора на бэкенде необходимо синхронно проверять, нужно ли CLI выравнивать.
