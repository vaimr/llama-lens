## 1. Предпосылки и цели

### 1.1 Предпосылки

- В локальной сети работают экземпляры llama.cpp llama-server (первый узел: ai.lan), запущенные на Qwen3.8-27B-Q6_K (27,32B параметров, tensor split на двух RTX 3080, с поддержкой визуального анализа).
- В настоящее время отсутствуют какие-либо средства визуализации для мониторинга нагрузки экземпляров: скорость генерации токенов, использование GPU / видеопамяти / температуры / энергопотребления, загрузка CPU, память, состояние процессов — всё приходится проверять через SSH + nvidia-smi + ручные команды.
- В будущем планируется подключение дополнительных узлов вывода; необходима схема мониторинга «одна страница на узел + единый портал».

### 1.2 Цели

1. Создать веб-панель мониторинга llama灵境, развернутую на локальной машине (один процесс, порт 8000), для удалённого мониторинга N узлов llama-server.
2. Каждый узел имеет отдельную панель деталей; страница портала агрегирует все узлы.
3. Обновление данных в реальном времени с шагом 1 секунда (настраиваемый), технологичный, динамичный визуальный стиль.
4. Подробное отображение всех данных, связанных с AI / llama (80+ параметров, полный список в §7).
5. Только отображение, без уведомлений об оповещениях; однако при превышении порогов значения должны подсвечиваться красным.

### 1.3 Цели вне диапазона (текущая версия)

- Без отправки оповещений (email / IM / webhook)
- Без долговременного хранения исторических данных (только кольцевой буфер в памяти, данные теряются при перезагрузке)
- Без аутентификации пользователей (инструмент для внутренней локальной сети)
- Без изменения конфигурации контролируемых узлов (без добавления параметра --metrics, без установки агентов)
- Без упаковки в Docker/K8s (запуск через run.sh; Docker — для последующих итераций)

## 2. Термины

| Термин | Описание |
|---|---|
| llama-server | Официальный HTTP-сервер вывода llama.cpp (данная сборка — кастомная llama-cpp-turboquant) |
| Slot (Слот) | Слот параллельного сеанса llama-server (-np 1 означает 1 слот) |
| tok/s | Количество генерируемых токенов в секунду |
| Скорость обработки prompt | Скорость префиллинга prompt-токенов (tok/s) |
| Tensor split | Разделение слоёв модели на несколько GPU (-ts 24,20) |
| Speculative decoding | Декодер с черновиком draft-mtp (--spec-type draft-mtp --spec-draft-n-max 3) |
| Узел | Один контролируемый узел вывода (зарегистрирован в hosts.yaml) |
| Портал | Главная страница со списком всех узлов (/) |
| Детали | Панель одного узла (/host/:id) |
| Подсветка порогов | Визуальное выделение при превышении порога (жёлтый = предупреждение / красный = опасность) |

## 3. Пользователи и сценарии использования

- **Пользователь**: Инженеры по эксплуатации AI-инфраструктуры / разработчики (внутренняя локальная сеть)
- **Сценарии использования**:
  1. Плановая проверка: открыть портал и одним взглядом увидеть состояние всех узлов
  2. Мониторинг задач: во время длительной задачи вывода наблюдать в реальном времени скорость токенов и нагрузку GPU
  3. Диагностика сбоев: при замедлении задачи проверить использование GPU, температуру, энергопотребление, PCIe-канал на аномалии
  4. Оценка ёмкости: проанализировать использование памяти / диска / контекста, чтобы определить, приближается ли экземпляр к пределу

## 4. Функциональные требования

### FR-01 Управление множеством узлов и конфигурация

- Узлы регистрируются в `config/hosts.yaml`: id, имя, адрес llama (host:port), SSH (host/port/user/password), интервал сбора, переопределение порогов
- Добавление/удаление узлов — только изменение конфигурации + перезапуск сервиса, без изменения кода
- Каждый узел мониторится независимо: сбой одного узла не влияет на другие узлы и на саму панель
- Первый узел — ai.lan (подробности тестовой среды см. Приложение A)

### FR-02 Портальная страница узлов (/)

- Верхняя панель бренда: логотип llama灵境, общее число узлов / число онлайн
- Стена карточек узлов (сетка), каждая карточка показывает:
  - Имя узла + индикатор статуса (зелёный пульсирующий — онлайн / красный — оффлайн / жёлтый — SSH отключён)
  - Имя модели + количество параметров
  - Скорость генерации токенов (большое число + спарклайн за 60с)
  - По одной полосе загрузки на GPU (одна строка на карточку)
  - Загрузка CPU, использование памяти
  - Подсветка при превышении порога (красная рамка + красный угол)
- Клик по карточке открывает страницу деталей /host/:id
- Портал также обновляется в реальном времени (1с)

### FR-03 Панель деталей одного узла (/host/:id)

- Полная компоновка см. 03-Документация по UI и взаимодействию.md §3; зоны:
  TopBar / зона реального обзора (4 карточки: 3 полосы + 1 прибор) / зона GPU (агрегировано по карточкам) / зона текущих задач генерации (карточка состояния + поток событий) / системная зона / зона процессов / зона модели и слотов / зона трендов (12 графиков, 3 группы)

### FR-04 Ключевые AI-метрики

- Позиции отображения: скорость / использование контекста — как полосы (для использования контекста большое число — исходное количество токенов, процент в правом верхнем углу); вероятность принятия MTP — как прибор (цвет зависит от значения), все в зоне реального обзора (см. §3.3 документа 03-UI); статус задачи и поток событий — в зоне текущих задач генерации (§3.4)
- Скорость генерации токенов (tok/s): текущее значение + спарклайн + историческая кривая
  - Основной источник данных: лог tg_3s (скорость за 3-секундное окно, рассчитывается на сервере, точнее); резервный: дифференциал /slots n_decoded
- Скорость обработки prompt (tok/s): то же самое
  - Основной источник данных: строка лога "prompt processing" (текущая скорость + прогресс %); резервный: дифференциал /slots n_prompt_tokens_processed
- Использование контекста: использовано/всего и процент
  - Основной источник данных: строка лога "release" n_tokens (авторитетное значение, включая системный промпт); резервный: /slots (n_prompt_tokens + n_decoded)
  - Отображение: использовано (большое число исходных токенов), процент (правый верхний угол), остаток, всего (n_ctx, шкала до предела и деления), было ли усечение (truncated)
- Статус задачи: выполняется / в ожидании, ID задачи, оставшиеся токены (n_remain), накопленные декодированные токены текущей задачи (n_decoded)
- Статистика задачи: при завершении задачи записываются общее число токенов, затраченное время, средняя скорость, вероятность принятия MTP, использование контекста (попадает в поток событий)

### FR-05 Мониторинг GPU (агрегировано по карточкам)

- Для каждой GPU — отдельная панель, содержащая все метрики этой карточки:
  - Загрузка (круговой прибор)
  - Видеопамять: used/free/total + полоса прогресса
  - Температура, энергопотребление (draw/limit), обороты вентилятора, частота графического процессора, частота видеопамяти
  - PCIe-канал (gen/width), состояние производительности (P-state)
  - Версия драйвера, модель GPU
  - Процессы, использующие GPU (pid/name/видеопамять)
- Исторические кривые: загрузка, видеопамять (по одной линии на GPU)

### FR-06 Мониторинг системных ресурсов

- CPU: модель, число ядер, общая загрузка машины, загрузка каждого ядра (по одной полосе на ядро), load 1/5/15, тактовая частота
- Память: total/used/free/buff_cache/available, swap used/total
- Диск: для каждой точки монтирования size/used/avail/процент + скорость чтения/записи
- Сеть: для каждого сетевого интерфейса скорость rx/tx и накопленные значения
- Система: имя хоста, ядро, версия ОС, uptime, общее число процессов

### FR-07 Мониторинг процессов

- Карточка процесса llama-server:
  - PID, текущий CPU% (дифференциал), накопленный CPU%, RSS, VSZ, число потоков, время работы
  - Состояние systemd-сервиса (имя unit / описание / active / время запуска / накопленный CPU сервиса / память сервиса с пиком / число Tasks)
  - Полный командный вызов (сворачиваемый) + таблица распознанных параметров (model, mmproj, n-gpu-layers, flash-attn, tensor-split, batch, ubatch, np, ctx-size, kv-offload, cache-type-k/v, fit, threads, threads-batch, threads-http, temperature, top-p, top-k, spec-type, spec-draft-n-max, port, host)
- Топ-процессы: по CPU Top 8, по памяти Top 8 (pid/name/cpu%/mem%/rss)

### FR-08 Детали модели и слотов

- Информация о модели: имя, путь, ftype, число параметров, размерность embedding, размер словаря, размер файла, размер mmproj, модальности (vision/video/audio), n_ctx, n_ctx_train, vocab_type, capabilities, owned_by
- Детали слотов: id, статус, ID задачи, prompt-токены (всего/обработано/кэш), декодированные, оставшиеся, использование контекста%, полные параметры сэмплирования (temperature, dynatemp_*, top_k, top_p, min_p, top_n_sigma, xtc_*, typical_p, repeat_last_n, repeat_penalty, presence_penalty, frequency_penalty, dry_*, mirostat_*, adaptive_*, max_tokens, n_predict, n_keep, n_discard, ignore_eos, stream, n_probs, min_keep, chat_format, reasoning_format, reasoning_in_content, generation_prompt, samplers, speculative.types, timings_per_token, post_sampling_probs, backend_sampling, lora)

### FR-09 Исторические графики трендов

- Типы графиков (12 графиков, 3 группы, смежные метрики рядом):
  - llama-группа: скорость генерации токенов, скорость префиллинга, **использование контекста (линия сэмплирования 1с + справочная линия предела n_ctx)**, **вероятность принятия MTP (ступенчатый тренд по каждой задаче)**
  - GPU-группа: загрузка (по GPU), видеопамять (по GPU), температура (по GPU), энергопотребление (по GPU)
  - Системная группа: CPU, память (used/buff_cache, стопка), сеть (rx/tx), средняя нагрузка (три линии 1/5/15)
- Переключение временного окна: 5m / 15m / 1h
- Источник данных: кольцевой буфер в памяти (llama 3600 точек @1с, узел 1800 точек @2с)
- При разрыве соединения кривая прерывается (без интерполяции), сохраняется последнее значение

### FR-10 Поток событий

- Типы событий: начало задачи, начало префиллинга (общее число prompt-токенов), завершение задачи (с общим числом токенов/временем/средней скоростью), смена модели, появление/исчезновение llama, отключение/переподключение SSH, пересечение порогов (обновление уровня оповещения / восстановление)
- Отображение в стиле терминала, автоматическая прокрутка, в памяти хранятся последние 200 событий
- Каждое событие: временная метка + уровень (info/warn/error) + описание

### FR-11 Механизм обновления в реальном времени

- Обновление по умолчанию каждые 1 секунду (основной канал — WebSocket)
- Управление обновлением на клиенте: реальный (WS) / 1с / 2с / 5с / пауза
- Интервал отправки на сервере настраивается на каждый узел (push_interval, по умолчанию 1с)
- Интервал сбора настраивается: llama 1с, SSH 2с (значения по умолчанию)
- При разрыве WS автоматическое переключение на HTTP-опрос с уведомлением

### FR-12 Подсветка порогов

- Двухуровневая шкала: жёлтый (warn) / красный (danger), таблица правил в §8
- Эффект подсветки: число становится красным + свечение рамки карточки + пульсирующая анимация
- Пороги можно переопределять для каждого узла
- Только визуальное отображение, без отправки уведомлений

### FR-13 Разбор логов llama-server

- Непрерывный tail systemd journal (journalctl -u llama-server), разбор следующих строк логов:
  - `print_timing ... n_decoded = X, tg = Y t/s, tg_3s = Z t/s` (каждые 3с при генерации): текущая скорость, средняя скорость задачи, число декодированных
  - `print_timing ... prompt processing, n_tokens = X, progress = P, t = T s / S t/s` (примерно каждые ~2с при префиллинге): прогресс prompt, скорость prompt
  - `print_timing ... prompt eval time / eval time / total time / graphs reused / draft acceptance` (итог завершения задачи): время prompt/декодирования/общее, число повторных использований CUDA-графов, **вероятность принятия MTP / число принятых / средняя длина принятия**
  - `release ... stop processing: n_tokens = X, truncated = T` (завершение задачи): **общее использование контекста, было ли усечение**
  - `get_availabl ... selected slot by LCP/LRU, f_sim_best = X, f_keep = Y` (новая задача): способ выбора слота, сходство LCP, **коэффициент сохранения KV-кэша**
  - `launch_slot_ ... task N, is_child = C` (начало задачи): ID задачи, является ли дочерней
  - Загрузочные логи (один раз при каждом запуске): путь модели, n_slots/n_ctx_slot/kv_unified, контекст MTP draft, обновление типа KV-кэша (например turbo3→q8_0), verbosity, адрес прослушивания, список предупреждений (CORS, уведомление об изменении порта и т.д.)
- Машинное состояние "что сейчас делает llama": обработка prompt (с прогрессом) / генерация (с числом декодированных и скоростью) / ожидание
- Если логи недоступны (SSH отключён / имя unit не совпадает) → резервное переключение на дифференциал /slots, пометка log_available=false
- Параметры MTP: статическая конфигурация (spec-type/spec-draft-n-max, из разбора командной строки) + статистика во время выполнения (вероятность принятия/средняя длина, из логов) — отображаются одновременно

### FR-14 Локальный CLI (llamalens)

- Полноэкранный TUI в стиле htop, запускаемый **локально** на контролируемом узле; отображает те же данные, что и страница деталей одного узла (FR-03~FR-13)
- Нулевые зависимости во время выполнения: один статический бинарный файл (Go, `CGO_ENABLED=0`), на целевом узле не требуются Go / Python / pip
- Прямой локальный сбор данных (без бэкенда, без записи в файлы, без изменения состояния llama-server):
  - llama HTTP API (`/slots`@1с, `/props`+`/v1/models`@30с)
  - Прямое чтение `/proc`@2с (CPU/память/диск/сеть/нагрузка/топ-процессы)
  - `nvidia-smi`@2с (GPU)
  - `systemctl show` + `journalctl -u <unit> -f` (состояние сервиса + поток событий логов, правила разбора те же, что в FR-13)
- Взаимодействие: `q` выход / `p` пауза / `t` тренды / `g` GPU; адаптация при изменении размера терминала; при выходе терминал автоматически восстанавливается (без остатков)
- Подсветка порогов и веб-панель используют одни и те же правила (§8)
- Требования к терминалу: ≥80×20, необходим интерактивный TTY; также доступен `--once` для одноразового текстового снимка (доступен без TTY)
- Имя процесса / unit / порт должны совпадать с узлом в hosts.yaml

## 6. Критерии приёмки

| Номер | Критерий | Способ проверки |
| -------| -------------------------------------------------------------------------------------------------| -----------------------------------|
| AC-01 | На портале отображается карточка узла ai.lan, статус онлайн, модель Qwen3.8-27B-Q6_K (27.32B) | Открыть / |
| AC-02 | При запущенной задаче на странице деталей скорость генерации токенов > 0 и совпадает с фактической; в ожидании — 0 | Сравнить с задачей на узле / отправить маленький запрос |

- Отправка оповещений (email/IM/webhook) — последующая итерация

- Мониторинг не-llama сервисов (docker и другие детальные мониторинги)
